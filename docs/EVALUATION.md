This file separates deterministic correctness from probabilistic extraction/proposal quality. The numbers in the product requirements are **release targets**, not measured results. The local runner is `evals/run.py`; its machine-readable reports are in `evals/results/`.

## Extraction metrics

One labeled supported requirement is the unit. A prediction counts as true positive only when it matches a labeled requirement, has the correct supported type/meaning and points to a valid source span. Unsupported invented requirements are counted separately. Define matching rules before running the held-out set; manually adjudicate ambiguous matches without reading hidden labels during model iteration.

| Metric | Calculation | Release target | Actual |
| --- | --- | ---: | --- |
| Full requirement precision | TP / (TP + FP) on all predicted requirements | ≥ 95% | Pending complete requirement labels and semantic review |
| Full requirement recall | TP / (TP + FN) on all labeled held-out requirements | ≥ 90% | Pending complete requirement labels and semantic review |
| Material fabrications | Unsupported binding requirements judged material | 0 goal | Pending human adjudication |
| Evidence-span alignment | Exact source offsets / all predicted requirements | Report | DEMO fixture: 60/60; semantic support unverified |
| Primary deliverable recall | Correctly covered labeled primary deliverables / all such labels | Diagnostic only | DEMO fixture: 30/30 |

Report TP, FP, FN and denominators as well as percentages. Empty-denominator cases require explicit handling; never report an unsupported 100%. Separate omissions, incorrect quantities, invented deadlines and unsupported deliverables. A fixture replay is useful for workflow determinism but is not evidence of live model extraction quality.

The generated ground truth has one labeled primary deliverable phrase per extraction brief, plus company, contact, timeline and budget fields. It does **not** enumerate every supported requirement in the prose. `demo-extraction` therefore checks whether a prediction with a valid source span and `deliverable` kind covers that labeled phrase. It leaves other predictions unadjudicated rather than treating them as true or false positives. This measures a narrow diagnostic recall; it cannot establish the 95%/90% release gate. Source-span alignment also cannot establish that an extracted statement has the right meaning, is binding, or is materially safe.

To measure the full gate, first annotate every supported requirement and its type, meaning, and evidence span for each held-out brief independently of extractor output; include zero-requirement cases and negative examples such as vague wishes, exclusions and future possibilities. Freeze those labels, then run the selected extractor and match predictions one-to-one against labels. Count unmatched predictions as FP and unmatched labels as FN; human adjudicators should review borderline paraphrases and material inventions. Record both the DEMO and connected model separately, with model/prompt versions and a bounded call budget. The synthetic 30-case extraction subset alone cannot establish real-customer accuracy.

## Deterministic gates

Run invariant/property-style tests for line totals, rounding boundaries, discounts, contingency, tax, threshold approval, noncatalog approval, version hashing, expiration, token binding, cross-workspace rejection, accepted immutability and concurrent repeated acceptance. Test PDF text against the approved quote version, including totals and line items, plus long names and multi-page pagination. CSV exports must neutralize leading spreadsheet formula characters. Exercise HubSpot adapter contract with recorded/mock responses and an ambiguous timeout; live HubSpot smoke test is separate.

## Proposal review

At least 10 generated proposals need a human review using a 0–3 rubric for each dimension: clarity of objective/scope, explicit exclusions and assumptions, feasible schedule/milestones, and traceability to source evidence/catalog. Record reviewer, proposal IDs/versions, date, scores and comments; summarize disagreements and required fixes. Do not substitute a model-as-judge result for human review. Without a completed sample, this release gate is pending.

## Browser and artifact review

Run the end-to-end demo at desktop and mobile sizes of 1440, 1024 and 390 px. Capture 6–8 real screenshots including brief intake, clarification, option comparison, approval/error, proposal preview, customer review and handoff. Inspect keyboard/focus behavior, clipped content, horizontal overflow and reduced motion. Inspect rendered PDF pages for page breaks, table overflow and matching source content. Screenshot paths and actual outcome belong in [`PORTFOLIO.md`](PORTFOLIO.md).
